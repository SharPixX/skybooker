# Yandex Air Pet Project 10/10 Plan

## Цель

Довести проект до уровня сильного портфельного full-stack pet project, который:

- выглядит как законченный продукт, а не набор экранов
- честно разделяет `demo mode` и `real mode`
- показывает инженерную зрелость, а не только красивый UI
- хорошо читается работодателем, тимлидом и на собеседовании
- стабильно запускается локально и легко демонстрируется

Это план не для enterprise-airline production, а для максимального качества именно как pet project.

## Что такое 10/10 для pet project

### Продукт

- понятный сценарий `поиск -> рейсы -> место -> бронь -> кабинет`
- нет ощущения сломанного или фейкового flow
- пользователь понимает, где реальные данные, а где demo

### Инженерия

- критические сценарии покрыты хотя бы базовыми тестами
- нет явных архитектурных дыр, которые сразу режут глаз ревьюеру
- backend и frontend имеют внятные границы ответственности

### Дизайн

- интерфейс выглядит цельно и запоминается
- есть единый visual system, а не случайный набор карточек
- mobile и desktop ощущаются как один продукт

### Демонстрация

- проект поднимается без боли
- есть seed/mock данные для показа
- README помогает быстро понять идею, стек и ограничения

## North Star

Итог должен ощущаться так:

- как очень сильный учебно-портфельный airline booking product
- как проект, в котором есть и вкус в интерфейсе, и мозги в backend
- как работа человека, который умеет доводить продукт до законченного состояния

## Главный принцип

Не пытаемся добить бесконечный enterprise scope.

Вместо этого делаем:

1. честный и стабильный demo experience
2. сильную архитектурную базу
3. продуманный UI/UX
4. хорошую упаковку проекта

## Антицели

Не делаем:

- молчаливую подмену backend на mock-данные
- псевдо-production, который выглядит реальным, но ломается при первом вопросе
- перегруженный UI ради красоты
- бессмысленную “enterprise-сложность”, которая не усиливает pet project

## Фаза 1. Развести demo mode и real mode

### Цель

Сделать проект честным и управляемым в двух режимах: демонстрационном и интеграционном.

### Что делаем

- вводим явный флаг режима приложения
- убираем silent fallback на mock-данные при ошибке API
- показываем заметное состояние `Demo mode`, если backend недоступен
- выносим mock-логику в отдельный понятный слой
- определяем, какие экраны разрешено показывать в demo, а какие нет

### Результат

- ревьюер сразу понимает, что demo-режим контролируемый
- проект перестает “врать” пользователю

## Фаза 2. Закрыть главные backend-дыры

### Цель

Убрать архитектурные проблемы, которые сильнее всего бьют по оценке проекта.

### Что делаем

- нормализуем email в auth
- делаем безопаснее смену пароля и стратегию инвалидирования сессии
- чиним graceful shutdown
- добавляем endpoint списка бронирований пользователя
- пересобираем booking flow так, чтобы `confirm` был честно помечен как demo-confirm, если платежки нет
- документируем ограничения платежного контура

### Результат

- backend начинает выглядеть как зрелый pet project, а не полу-демо

## Фаза 3. Довести кабинет до server-driven логики

### Цель

Сделать профиль и мои бронирования настоящей частью продукта.

### Что делаем

- убираем зависимость кабинета от `localStorage` как основного источника данных
- подключаем `My bookings` к backend
- показываем активные, отмененные и завершенные брони
- сохраняем local cache только как вторичный UX-слой, а не source of truth
- приводим состояния `loading / empty / error / success` к понятному виду

### Результат

- кабинет начинает выглядеть как настоящий продуктовый модуль

## Фаза 4. Добить booking flow до убедительного уровня

### Цель

Сделать главный пользовательский сценарий сильнейшей частью проекта.

### Что делаем

- упрощаем и полируем поиск
- доводим autocomplete и date picker до стабильного поведения
- делаем results page быстрее для сравнения
- усиливаем seat selection как операционный экран
- приводим booking page к честному сценарию:
  - статус брони
  - таймер удержания
  - понятные следующие шаги

### Результат

- путь покупки билета демонстрирует сильный продуктовый thinking

## Фаза 5. Frontend polish по skill frontend-design

### Цель

Довести визуальную систему до уровня, который запоминается.

### Направление

Берем курс на спокойный премиальный airline-интерфейс в духе Яндекса:

- ясная типографика
- плотная иерархия
- чистые поверхности
- сильный hero-search
- аккуратная motion-система

### Что делаем

- пересобираем design tokens
- стандартизируем surface hierarchy
- выравниваем header/footer/shell
- усиливаем типографику и spacing
- чистим визуальный шум
- делаем mobile-pass по основным страницам

### Результат

- проект выглядит не просто “красиво”, а собранно и профессионально

## Фаза 6. Тесты на критический домен

### Цель

Поднять доверие к проекту через минимально достаточное тестовое покрытие.

### Что делаем

- добавляем backend test runner
- пишем unit/integration тесты на:
  - register/login
  - booking seat
  - race/conflict на место
  - cancel booking
  - get my bookings
- добавляем хотя бы базовые frontend тесты на:
  - booking search params
  - auth context
  - критические рендеры пустых/error states

### Минимум для 10/10 pet project

- 5-8 хороших тестов лучше, чем 0 тестов и громкие обещания

### Цель

Сделать так, чтобы проект хорошо “продавал себя” без твоих устных пояснений.

### Что делаем

- пишем сильный README
- добавляем:
  - описание идеи проекта
  - стек
  - архитектуру
  - ключевые сценарии
  - как поднять локально
  - demo mode vs real mode
  - список известных ограничений
- добавляем свежие скриншоты основных экранов
- отдельно фиксируем, что в проекте интересно инженерно

### Результат

- GitHub-репозиторий начинает работать как портфолио-страница

## Фаза 8. Deployment и demo-ready инфраструктура

### Цель

Сделать проект удобным для показа.

### Что делаем

- приводим env-конфиг к чистому виду
- проверяем сборку frontend/backend с нуля
- делаем понятный `.env.example`
- готовим один стабильный сценарий запуска локально
- если нужно, готовим простой deploy path:
  - frontend preview/deploy
  - backend deploy
  - seeded database

### Результат

- проект можно показать за 2-3 минуты без шаманства
